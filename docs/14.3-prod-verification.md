# 14.3 — Production verification

Day 14, step 3. Written 9 Aug 2026, before the first production verification run.

This is the checklist for proving the live deployment works. Two things passed locally
and were not trusted in production until re-proven here: the Postgres exclusion
constraint under Neon's pooled connections, and the Auth.js edge/Node split on the real
Vercel runtime. Both are covered below, along with a full owner and customer
click-through.

Replace `<app>` throughout with the live Vercel URL. **Do the whole customer half on a
phone, on mobile data, not on wifi** — per V1-LAUNCH-PLAN's "What only you can verify".

---

## Decisions recorded here

### The local database was already pooled

`.env`'s `DATABASE_URL` points at `ep-patient-voice-asc9v67l-pooler...neon.tech` — a
**`-pooler`** host. So every local `npm run probe:constraint` was already going through
pgBouncer. V1-LAUNCH-PLAN 14.5's premise ("you proved it locally; serverless + pgBouncer
is a different execution environment") is half wrong: the pgBouncer half was in the loop
all along.

That does not make this step unnecessary — it narrows what it is for. What was genuinely
never proven is that the constraint exists **on the production Neon branch**, which is a
different database where `prisma migrate deploy` has never run, and that the app behaves
correctly under **serverless invocation-level** concurrency. Those are the two things
Test A and Test B below actually establish.

### `pgbouncer=true` stays off, in both environments

Decided 9 Aug 2026. `.env.example` used to document `?sslmode=require&pgbouncer=true`
while the real local `.env` has `?sslmode=require&channel_binding=require` and has always
worked.
Neon's pooler supports protocol-level prepared statements, so Prisma's prepared
statements survive transaction pooling without the flag.

**The decision is to leave the flag off local *and* production.** The reasoning is that
it matches what is already proven working, rather than that the flag is wrong. What
matters more than which way this went: **the production and local connection strings
must differ only in which branch they name.** If one carries the flag and the other
doesn't, the two environments aren't comparable and a prod-only pass proves less than it
appears to.

The failure this flag exists to prevent is `prepared statement "s0" already exists`
(SQLSTATE 42P05), appearing intermittently under concurrency. If that ever shows up in
production, this decision is what to revisit first — add the flag to both environments,
not just the one that failed.

`.env.example` was updated the same day to match: the flag is gone from its example URL,
and the comment above it carries the reasoning and the `42P05` symptom that would justify
revisiting, so nobody "fixes" it back by adding the flag to one environment only.

## Item 2 first: the Auth.js edge/Node split is already resolved

Confirmed 9 Aug 2026, before any deployment, so this needs no runtime test of its own.

`src/proxy.ts`'s own comments state it: Next 16's proxy convention always runs on the
Node.js runtime, so the split is no longer a *runtime compatibility* constraint. The file
still imports `auth.config` rather than `auth`, for a different and still-valid reason —
the matcher accepts nearly every request, and the Prisma-backed config would open a
database connection on each one just to decide whether a JWT is present.

Verified against the build output rather than taken on the comment's word:

- `.next/server/middleware-manifest.json` is `{"middleware":{},"sortedMiddleware":[],"functions":{}}`
  — the proxy is **not** registered as an edge function. An edge middleware would appear
  in `sortedMiddleware`.
- `.next/server/middleware.js` is CommonJS `require()` against the Node turbopack
  runtime, and has a `.nft.json` node file trace — only emitted for Node.js server
  bundles.
- That trace lists **89 files, zero matching `prisma`, `bcrypt`, or `.prisma`.** The
  dependency-free half is genuinely dependency-free, verified structurally rather than by
  reading imports.
- `src/proxy.ts` last changed 25 Jul (`fe8a36c`); the build is from 8 Aug. The evidence
  is current, not stale.

So there is no edge-runtime incompatibility left to fail on. What remains unverified on
Vercel is not the split but three runtime facts: that the proxy executes at all, that
`AUTH_SECRET` is set so the JWT decodes, and that `AUTH_URL`/`NEXTAUTH_URL` don't
misroute the callback. Checks **O1–O3** cover exactly those.

## Test A — the exclusion constraint, against the prod pooled URL

`scripts/probe-exclusion-constraint.ts` already asserts both directions and drives the
real `createBooking()` path, including the SQLSTATE → `SLOT_TAKEN` translation. It needs
no changes. It only needs to be pointed at production.

### Before running it

- [ ] Understand that it **writes real rows** into whatever `DATABASE_URL` names.
      Everything lands in a dedicated tenant (`probe-tenant` / slug `probe-exclusion`)
      deleted before *and* after the run, in a `finally` block so it cleans up on failure
      too. It cannot reach `seed-tenant-demo`.
- [ ] Understand that the `NODE_ENV === "production"` guard in the script **does not
      protect production.** It reads the *script's* environment, not the target database.
      Pointing `DATABASE_URL` at prod sails straight past it.
- [ ] Use the **pooled** URL (the host with `-pooler` in it), not `DIRECT_URL`. Using the
      direct URL would skip the exact thing being re-proven.
- [ ] `DIRECT_URL` must also be set, because `schema.prisma` declares it. It is not what
      the probe connects over.
- [ ] Confirm the prod URL differs from the local one **only in which branch it names** —
      no `pgbouncer=true` on either, per the decision above.

Verified 9 Aug 2026: `.env` does **not** override a shell-set `DATABASE_URL` (dotenv
never overwrites an existing variable), so this genuinely retargets with no silent
fallback to the dev branch.

### Run it

```powershell
$env:DATABASE_URL = "<prod POOLED url — the host with -pooler in it>"
$env:DIRECT_URL   = "<prod DIRECT url>"
npm run probe:constraint *> prod-constraint.txt
"EXIT=$LASTEXITCODE"
Get-Content prod-constraint.txt
```

Redirect with `*>`, then read `$LASTEXITCODE`. Do not pipe into `Tee-Object` or
`Select-Object` and read `$?` — per CLAUDE.md that reports the cmdlet's status and shows
`True` over a failing probe.

**Afterwards, close that terminal window.** `$env:DATABASE_URL` persists for its whole
life, and the next `npm run db:seed` or `prisma migrate dev` typed into it hits
production. This is the most likely way to damage the production database today.

### The exact output to expect

Verbatim from a real run against the Neon dev branch on 9 Aug 2026, so this is a literal
baseline rather than a reconstruction:

```
> barber-saas@0.1.0 probe:constraint
> tsx scripts/probe-exclusion-constraint.ts

Probing ep-XXXX-pooler.c-4.eu-central-1.aws.neon.tech/neondb

Constraint installed:
  EXCLUDE USING gist ("staffId" WITH =, tsrange("startAt", "blockedUntil") WITH &&) WHERE ((status = ANY (ARRAY['CONFIRMED'::"BookingStatus", 'COMPLETED'::"BookingStatus"])))

  PASS  pre  range is over blockedUntil (not endAt), so buffer is enforced under concurrency
  PASS  pre  WHERE clause covers COMPLETED, so completing a booking does not reopen its slot
  PASS  pre  keyed by staffId
  PASS  A  overlap 10:00-10:30 vs 10:15-10:45, fired concurrently -> expected 1 created + 1 SLOT_TAKEN, got 1 created + 1 SLOT_TAKEN
  PASS  B  back-to-back 10:00-10:30 then 10:30-11:00, buffer 0 -> expected both created, got created + created
  PASS  C  same adjacency, buffer 15 (blocks to 10:45) -> expected created + SLOT_TAKEN, got created + SLOT_TAKEN
  PASS  D  identical slot, different staff -> expected both created, got created + created
  PASS  E  rebook a CANCELLED booking's slot -> expected created, got created
  PASS  F  rebook a COMPLETED booking's slot -> expected SLOT_TAKEN, got SLOT_TAKEN

  PASS  count  9 of 9 checks ran

All phases passed. The database is the authority on slot conflicts.
```

Exit code `0`.

**The acceptance rule is a diff, not a read-through: the only line that may differ from
the local run is the `Probing` line.**

Postgres normalises the migration's `status IN ('CONFIRMED','COMPLETED')` into
`= ANY (ARRAY[...]::"BookingStatus")`. That rewrite is expected and is what a correctly
applied migration looks like — it is not drift.

- [ ] Test A run against the prod pooled URL
- [ ] Output diffed against the baseline above; only the `Probing` line differs
- [ ] `EXIT=0`
- [ ] Terminal window closed

### Failure signatures

| What you see | Cause | Fix |
|---|---|---|
| `Constraint "no_overlapping_bookings" is not installed on this database.` and nothing else | `migrate deploy` didn't run, ran against the wrong branch, or `CREATE EXTENSION btree_gist` failed | Re-run `prisma migrate deploy` with `DIRECT_URL` on the prod branch. Never `db push` |
| Only `Probing` prints, then `PrismaClientInitializationError` / `Can't reach database server` | Wrong URL, or `sslmode` missing | Check the connection string |
| `FAIL A ... got 1 created + 0 SLOT_TAKEN` plus a raw `PrismaClientUnknownRequestError` | The constraint fired but `isSlotTakenError` didn't match the message the prod pooler produces | The important one — the customer would see `{status:"error"}` instead of "someone got there first". Fix the matcher in `lib/db/bookings.ts` against the actual message text |
| `FAIL A ... got 2 created + 0 SLOT_TAKEN` | The constraint exists but isn't being enforced. **Stop. Do not demo.** | Should be impossible if the `pre` checks passed; investigate before anything else |
| `prepared statement "s0" already exists` (42P05), intermittently | Prisma's prepared statements vs. transaction pooling | Revisit the `pgbouncer=true` decision above — add it to **both** environments, not just the one that failed |
| `FAIL count 6 of 9 checks ran` | A phase threw and the run exited early | Read the stack above it; a partial run is not a pass |

### What Test A does and does not prove

**Proves:** the constraint exists on the production database, is shaped correctly,
rejects real overlaps under genuinely simultaneous inserts through the production pooler,
permits genuine adjacency, honours `bufferMinutes`, and surfaces as `SLOT_TAKEN` rather
than an exception. Phase A's two `createBooking` calls take two different connections
from Prisma's pool, so they become two different pgBouncer server connections and really
do race inside Postgres.

**Does not prove:** anything about Vercel. One process, one Prisma client, warm
connections. That is Test B.

`probe:cancel` and `probe:rate-limit` use their own throwaway tenants and can be pointed
at prod the same way if wanted. `probe:crud`'s blast radius has not been checked — read
it before running that one against production.

## Test B — serverless concurrency, through the live URL

There is no clean way to fire concurrent Server Action POSTs by hand: the action id lives
in a client chunk and the payload is Next-internal. Driving it properly would need a
browser-automation dependency, which is CLAUDE.md rule 4 territory and not worth it for
one check. So this is manual.

- [ ] Two devices (or a phone plus a laptop private window). On both: `/b/kastanien-barbershop`,
      **same service**, **same date and time**, barber left on **Any barber**.
- [ ] Get both to the final confirm screen with customer details filled in — **different
      phone numbers on each**, or the per-phone rate limiter becomes the thing being tested.
- [ ] Tap Confirm on both within about a second.

**Correct behaviour:** exactly one lands on `/b/kastanien-barbershop/booked/<token>`. The
other gets a recoverable message and a fresh slot list — most likely `staff_taken` ("that
barber just got booked", one tap to retry with a colleague), or `slot_taken` if only one
barber was free at that instant. Neither shows a generic error, and the calendar ends up
with **exactly one** booking in that slot.

**What this tests:** the customer-visible outcome end to end on the real runtime. It does
*not* isolate the constraint — at human timing the pre-insert availability re-check in
`app/(public)/b/[slug]/book/actions.ts` will usually reject the loser before the insert is
attempted, and no log line distinguishes which layer caught it. That is fine and
deliberate: `classifyMiss` is shared by both paths so the two are indistinguishable by
design. Test A proves the constraint; Test B proves the app on Vercel behaves correctly
when two people collide.
